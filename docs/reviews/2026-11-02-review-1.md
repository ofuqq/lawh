## 1. Executive Summary

Ruqa has achieved significant architectural milestones in its initial sprint:
1. **Three-Crate Clean Architecture**: Strict boundaries are respected. `ruqa-core` is pure data models, geometry, and serialization with zero UI or GPU dependencies. `ruqa-render` contains CPU-first rasterization via `tiny-skia` and `parley` with zero windowing dependencies. `ruqa-app` isolates native OS windowing via `winit 0.30` and `softbuffer`.
2. **Quality & Compliance Excellence**: All workspace formatting, clippy linter checks (`-D warnings`), test suites, and `cargo-deny` license/source audits pass with zero warnings or errors. Zero `unsafe` code exists anywhere in the codebase.
3. **M1 Rendering Engine Fidelity**: Hand-drawn sketchy shapes via `roughr` OpSet conversion and velocity-smoothed Catmull-Rom freehand pen strokes are fully implemented and verified in `ruqa-render`.
4. **Current Interactive Reality (Truth Check)**: When running `cargo run -p ruqa-app`, the window opens to an empty `#121212` canvas because interactive element creation tools (toolbar and keyboard shortcuts) were deferred to Milestone M3. Panning and zooming function mathematically in memory, but are visually undetectable without visible canvas elements or a dot grid. Issue [#84](https://github.com/ofuqq/ruqa/issues/84) has been filed to introduce a `--demo` flag providing immediate visual exploration.
5. **Key Bug Discoveries**: Six distinct bugs were discovered during source audit and live X11 driving, including stale selection marquee artifacts, a 30-36% idle CPU event loop spin, HiDPI viewport distortion, non-circular ellipse hit-test radial distortion, and a corrupted Latin font asset. All have been documented and filed on GitHub.

## 2. Truth Check on Closed Work (Milestones M0 & M1)

A detailed review was conducted to evaluate why running `ruqa-app` after Milestone M1 presented an empty dark canvas.

### The Two Core Questions:
1. **Can a user draw in the real app today?**
   **NO.** In `crates/ruqa-app`, left-click mouse inputs are hardcoded exclusively to selection hit-testing and marquee dragging (`selection.rs`). There is no active drawing tool state machine, no pen inking handler, and no shape creation dispatcher in `ruqa-app`. While `ruqa-render` contains complete rendering functions (`shape_render::render_element`, `pen_render::render_pen_stroke`), they cannot be invoked interactively by a user running the desktop app today.
2. **Can a user pan and zoom in the real app today?**
   **In memory YES; visually NO.** 
   - `handle_cursor_moved` correctly updates `self.viewport.pan_by` when holding `Space` or the middle mouse button.
   - `handle_mouse_wheel` correctly updates `self.viewport.zoom_at` centered at the cursor coordinate.
   - **However**, because the scene graph initializes with zero elements, and because the canvas does not yet render background orientation grid dots (scheduled for [#31](https://github.com/ofuqq/ruqa/issues/31)), every pixel on the canvas remains solid matte black (`#121212`). Panning and zooming produce zero visible pixel changes, giving the appearance of a frozen or broken window.

### Status of Closed M0–M1 Issues
- **#8 (winit window init)**: Verified working. Window opens centered on screen with minimum and default constraints.
- **#9 (softbuffer presentation)**: Verified working. Clear frame and pixmap blitting are fully functional.
- **#10 (viewport transforms)**: Verified working in `ruqa-core`. Screen-to-world and world-to-screen matrix math is accurate.
- **#11 (pan and zoom inputs)**: Verified working in dispatch; needs visual orientation (grid or demo shapes).
- **#12 (roughr OpSet to tiny-skia converter)**: Verified working. Converts MultiStroke and Fill paths deterministically.

## 3. Empirical Benchmarks & Hardware Performance

All benchmarks were executed directly on the host machine (Intel Core i5-8250U @ 1.60GHz, 4 cores / 8 threads):

### Spike 1: 2D Rasterization Throughput (`spike1_bench`)
Profiling `tiny-skia` CPU rasterization of hand-drawn shapes at 1920x1080 32-bit RGBA:

| Element Count | Mean Latency | Effective FPS | Resident Memory (RSS) | Evaluation |
|---|---|---|---|---|
| **50 elements** | $8.62\text{ ms}$ | $116.0\text{ FPS}$ | $11.34\text{ MB}$ | **PASSED** ($< 16.67\text{ ms}$) |
| **100 elements** | $14.79\text{ ms}$ | $67.6\text{ FPS}$ | $11.36\text{ MB}$ | **PASSED** ($< 16.67\text{ ms}$) |
| **250 elements** | $28.94\text{ ms}$ | $34.6\text{ FPS}$ | $11.40\text{ MB}$ | Below 60 FPS ($> 16.67\text{ ms}$) |
| **500 elements** | $71.82\text{ ms}$ | $13.9\text{ FPS}$ | $11.45\text{ MB}$ | Unculled Drop |
| **1,000 elements** | $113.52\text{ ms}$ | $8.8\text{ FPS}$ | $11.52\text{ MB}$ | Unculled Drop |

### Spike 2: Arabic Text Shaping & BiDi Layout (`spike2_bench`)
Profiling `parley` HarfRust shaping across 100 iterations of a 440-character bilingual passage:
- **Tested String**: `"خوارزمية Dijkstra تعمل في O(V log V)"` + bilingual algorithm text.
- **Arabic Cursive Connected**: `true` (all medial, initial, and final ligatures properly joined).
- **Latin Tokens Strictly Isolated**: `true` (Latin words and math equations stay strictly LTR inside RTL flow).
- **Shaping Latency**:
  - Mean: **$0.886\text{ ms}$**
  - Minimum: **$0.680\text{ ms}$**
  - Maximum: **$1.611\text{ ms}$**
- **Verdict**: Far surpasses the $< 5.0\text{ ms}$ budget by $5.6\times$.

### Render Microbenchmarks (`cargo bench -p ruqa-render -- --test`)
Stress testing unculled full-scene rasterization:
- **1,000 elements**: $99.99\text{ ms}$ ($10.0\text{ FPS}$)
- **5,000 elements**: $522.43\text{ ms}$ ($1.9\text{ FPS}$)
- **10,000 elements**: $1,118.99\text{ ms}$ ($0.9\text{ FPS}$)

### Performance Takeaway & Spatial Culling Mandate
The empirical data shows that CPU rasterization easily delivers $\ge 60\text{ FPS}$ for scenes up to 100 actively visible shapes with tiny memory usage ($< 12\text{ MB}$). However, unculled rasterization scales as $O(N)$ and degrades below interactive thresholds at 250+ elements. Therefore, **Spatial Viewport Culling ([#32](https://github.com/ofuqq/ruqa/issues/32)) is a mandatory requirement for v0.1.0**.

## 5. Architectural & ADR Decisions

### ADR 0003: CPU-First 2D Rendering Pipeline (`tiny-skia` + `softbuffer`)
- **Decision**: **Accepted (with Culling Condition)**.
- **Rationale**: CPU software rasterization delivers rock-solid cross-platform compatibility across Linux (X11/Wayland), macOS, and Windows with zero GPU driver headaches. It passes headless CI effortlessly. Viewport culling ([#32](https://github.com/ofuqq/ruqa/issues/32)) ensures that only visible items enter the rasterizer, keeping frames well under $16.6\text{ ms}$. Dynamic tile caching and rayon multithreading are deferred post-v0.1.

### ADR 0007: Text Layout & Shaping Engine (`parley`)
- **Decision**: **Accepted**.
- **Rationale**: Empirical test latency is $0.886\text{ ms}$ for 440 characters. HarfRust shaping produces unbroken Arabic cursive with zero detached letters, and strictly isolates embedded English variables and math expressions ($O(V \log V)$). Dependencies pass `cargo-deny` with zero conflicts.

### ADR 0008: UI Chrome Toolkit Selection
- **Decision**: **Accepted: Option 2 (Custom Minimal CPU Chrome)**.
- **Rationale**:
  1. *Zero-GPU Guarantee*: Using `egui` would force GPU initialization (`wgpu`) or heavy software mesh rasterization (`egui_tiny_skia`), violating Ruqa's zero-GPU rule.
  2. *Memory Footprint*: Process stays under $12\text{ MB}$ RSS.
  3. *Scope Simplicity*: Ruqa's UI chrome is intentionally minimalist (a floating top HUD toolbar with 8 buttons, a property pill, and a simple folder sidebar). Implementing this directly with `tiny-skia` vector shapes and `parley` text requires $< 350\text{ LOC}$, maintaining strict file limits without pulling in thousands of third-party widget abstractions.

## 9. Actionable Recommendations

### For the Builder Agent:
1. **Fix Event Loop Idle Spin ([#88](https://github.com/ofuqq/ruqa/issues/88))**: Set `event_loop.set_control_flow(ControlFlow::Wait)` in `main.rs` to drop idle CPU usage from 35% to 0%.
2. **Fix Stale Marquee Artifact ([#87](https://github.com/ofuqq/ruqa/issues/87))**: Call `self.request_redraw()` on `WindowEvent::MouseInput` transitions.
3. **Multiply Viewport Transform by HiDPI Scale ([#90](https://github.com/ofuqq/ruqa/issues/90))**: Ensure `Presenter::pixmap` rendering scales properly on 4K/Retina displays.
4. **Fix Ellipse Hit-Testing Math ([#91](https://github.com/ofuqq/ruqa/issues/91))**: Calculate eccentric anomaly $t = \operatorname{atan2}(dy \cdot rx, dx \cdot ry)$ for boundary projection.
5. **Replace Corrupted Roboto Font ([#92](https://github.com/ofuqq/ruqa/issues/92))**: Download the binary TTF from Google Fonts repository.
6. **Implement Demo Board CLI Flag ([#84](https://github.com/ofuqq/ruqa/issues/84))**: Provide sample shapes on startup so testers can interact with the whiteboard before toolbar tools land.

### For the Owner:
1. **System Packages**: Install `xorg-server-xvfb`, `xdotool`, and `imagemagick` to enable automated GUI testing in your local Arch environment.
2. **Dogfooding Workflow**: Once PR [#84](https://github.com/ofuqq/ruqa/issues/84) lands, run `cargo run -p ruqa-app -- --demo` to interactively pan, zoom, select, and drag vector shapes on the live canvas.
